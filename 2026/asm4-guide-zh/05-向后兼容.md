# 5. 向后兼容

## 5.1 引言

过去，类文件格式中曾引入过新的元素，将来也还会继续添加新的元素（例如为模块化、Java 类型上的注解等）。直到 ASM 3.x，每一次这样的变化都会导致 ASM API 出现向后不兼容的改动，这并不好。为了解决这些问题，ASM 4.0 中引入了一种新机制。其目标是确保未来所有 ASM 版本都能与之前的任何版本保持向后兼容，一直回溯到 ASM 4.0，即使类文件格式中引入了新特性也是如此。这意味着，从 4.0 开始，为某一个 ASM 版本编写的类生成器、类分析器或类适配器，仍然可以在未来任何 ASM 版本中使用。然而，这一性质无法仅由 ASM 自身来保证。它要求用户在编写代码时遵循若干简单的指南。本章的目标就是介绍这些指南，并说明 ASM Core API 内部用于确保向后兼容性的机制。

> **注意**：ASM 4.0 中引入的向后兼容机制要求把 `ClassVisitor`、`FieldVisitor`、`MethodVisitor` 等从接口改为抽象类，并带有一个以 ASM 版本为参数的构造器。如果你的代码是为 ASM 3.x 实现的，可以通过把代码分析器和适配器中的 `implements` 替换为 `extends`，并在其构造器中指定 ASM 版本来把它升级到 ASM 4.0。此外，`ClassAdapter` 和 `MethodAdapter` 已被合并到 `ClassVisitor` 和 `MethodVisitor` 中。要转换你的代码，只需把 `ClassAdapter` 替换为 `ClassVisitor`，把 `MethodAdapter` 替换为 `MethodVisitor`。同样，如果你定义过自定义的 `FieldAdapter` 或 `AnnotationAdapter` 类，现在可以把它们替换为 `FieldVisitor` 和 `AnnotationVisitor`。

### 5.1.1 向后兼容契约

在介绍确保向后兼容性的用户指南之前，我们在这里更精确地定义「向后兼容」的含义。首先，重要的是研究新的类文件特性如何影响代码生成器、分析器和适配器。也就是说，抛开任何实现和二进制兼容性问题，一个在这些新特性引入之前设计的类生成器、分析器或适配器，在这些修改之后是否仍然有效？换言之，如果我们假设这些新特性被简单地忽略，并原封不动地通过一条在其引入之前设计的变换链，这条链是否仍然有效？事实上，对类生成器、分析器和适配器的影响是不同的：

- 类生成器不受影响：它们用某个固定的类版本生成代码，而这些生成的类在未来 JVM 版本中仍然有效，因为 JVM 保证了向后的二进制兼容性。
- 类分析器可能受影响，也可能不受影响。例如，一段为 Java 4 编写的、分析字节码指令的代码，尽管引入了注解，很可能仍能处理 Java 5 的类。但同一段代码很可能无法再处理 Java 7 的类，因为它无法忽略新的 `invokedynamic` 指令。
- 类适配器可能受影响，也可能不受影响。死代码删除工具不会受到注解引入的影响，甚至也不会受到新的 `invokedynamic` 指令的影响。另一方面，类重命名工具则两者都受影响。

这表明新的类文件特性可能对已有的类分析器或适配器产生不可预知的影响。如果这些新特性被简单地忽略并原封不动地通过一条分析或变换链，那么有时这条链会无错误地运行并产生有效结果，有时它会无错误地运行但产生无效结果，有时它会在执行过程中失败。第二种情况尤其成问题，因为它在用户毫无察觉的情况下破坏了分析或变换链的语义。这可能导致难以发现的缺陷。为解决这一问题，我们认为与其忽略新特性，不如在分析或变换链中一旦遇到未知特性就立即抛出错误。该错误表明这条链对于新的类格式可能有效也可能无效，其作者必须分析具体情况并在必要时更新它。

所有这些引出了以下向后兼容契约的定义：

- ASM 版本 X 是为版本小于或等于 x 的 Java 类编写的。它不能生成版本 y > x 的类，并且如果在 `ClassReader.accept` 中作为输入接收到版本大于 x 的类，它必须失败。
- 为 ASM X 编写并遵循下面介绍的指南的代码，必须能够在 ASM 的任何未来版本 Y > X 下，不加修改地继续处理版本最高为 x 的输入类。
- 为 ASM X 编写并遵循下面介绍的指南的代码，必须能够在 ASM Y 或任何未来版本下，不加修改地继续处理那些声明版本为 y、但只使用了版本小于或等于 x 中所定义特性的输入类。
- 为 ASM X 编写并遵循下面介绍的指南的代码，在 ASM X 或任何其他未来版本下，如果输入类使用了在类版本 y > x 中引入的特性，则必须失败。

注意，最后三点不涉及类生成器，因为它们没有类输入。

### 5.1.2 一个例子

为了说明用户指南以及 ASM 内部确保向后兼容的机制，我们在本章中假设向 Java 8 类中添加两个假想的新属性，一个用于存储类的作者，一个用于存储其许可证。我们还假设这两个新属性将在 ASM 5.0 中通过 `ClassVisitor` 的两个新方法暴露出来：

```java
void visitLicense(String license);
```

用于访问许可证，以及一个新版本的 `visitSource`，用于在访问源文件名和调试信息的同时访问作者[^1]：

```java
void visitSource(String author, String source, String debug);
```

旧的 `visitSource` 方法仍然有效，但在 ASM 5.0 中被声明为已废弃：

```java
@Deprecated void visitSource(String source, String debug);
```

作者和许可证属性是可选的，也就是说，调用 `visitLicense` 不是强制的，并且在 `visitSource` 调用中 `author` 可以为 `null`。

## 5.2 指南

本节介绍使用 ASM Core API 时必须遵循的指南，以确保你的代码在未来任何 ASM 版本中都保持有效（有效性的含义依据上述契约）。

首先，如果你编写的是类生成器，那么没有需要遵循的指南。例如，如果你为 ASM 4.0 编写一个类生成器，它很可能包含一个 `visitSource(mySource, myDebug)` 调用，当然不会调用 `visitLicense`。如果你不加修改地用 ASM 5.0 运行它，这会调用已废弃的 `visitSource` 方法，但 ASM 5.0 的 `ClassWriter` 会在内部把它重定向到 `visitSource(null, mySource, myDebug)`，从而得到预期的结果（但比把你的代码升级为直接调用新方法时效率略低）。同样，缺少对 `visitLicense` 的调用也不会有问题（生成的类版本也不会改变，而且该版本的类本来就不应该有许可证属性）。

另一方面，如果你编写的是类分析器或类适配器，即如果你覆写 `ClassVisitor` 类（或 `FieldVisitor`、`MethodVisitor` 等任何其他类似类），则必须遵循下面介绍的若干指南。

### 5.2.1 基本规则

这里我们考虑直接扩展 `ClassVisitor` 的类的简单情况（对其他访问者类的讨论和指南是相同的；间接子类的情况将在下一节讨论）。在这种情况下只有一条指南：

**指南 1**：要用 ASM 版本 X 编写 `ClassVisitor` 的子类，请以该确切版本为参数调用 `ClassVisitor` 构造器，并且绝不要覆写或调用在这个版本的 `ClassVisitor` 类中已废弃的方法（或在后续版本中才引入的方法）。

就这样。在我们的示例场景中（参见 5.1.2 节），为 ASM 4.0 编写的类适配器必须像这样：

```java
class MyClassAdapter extends ClassVisitor {
    public MyClassAdapter(ClassVisitor cv) {
        super(ASM4, cv);
    }
    ...
    public void visitSource(String source, String debug) { // 可选
        ...
        super.visitSource(source, debug); // 可选
    }
}
```

一旦针对 ASM 5.0 更新，`visitSource(String, String)` 必须被删除，因此该类必须像这样：

```java
class MyClassAdapter extends ClassVisitor {
    public MyClassAdapter(ClassVisitor cv) {
        super(ASM5, cv);
    }
    ...
    public void visitSource(String author,
            String source, String debug) { // 可选
        ...
        super.visitSource(author, source, debug); // 可选
    }
    public void visitLicense(String license) { // 可选
        ...
        super.visitLicense(license); // 可选
    }
}
```

这是如何实现的？在内部，ASM 4.0 中 `ClassVisitor` 的实现如下：

```java
public abstract class ClassVisitor {
    int api;
    ClassVisitor cv;
    public ClassVisitor(int api, ClassVisitor cv) {
        this.api = api;
        this.cv = cv;
    }
    ...
    public void visitSource(String source, String debug) {
        if (cv != null) cv.visitSource(source, debug);
    }
}
```

在 ASM 5.0 中，这段代码变成：

```java
public abstract class ClassVisitor {
    ...
    public void visitSource(String source, String debug) {
        if (api < ASM5) {
            if (cv != null) cv.visitSource(source, debug);
        } else {
            visitSource(null, source, debug);
        }
    }
    public void visitSource(Sring author, String source, String debug) {
        if (api < ASM5) {
            if (author == null) {
                visitSource(source, debug);
            } else {
                throw new RuntimeException();
            }
        } else {
            if (cv != null) cv.visitSource(author, source, debug);
        }
    }
    public void visitLicense(String license) {
        if (api < ASM5) throw new RuntimeException();
        if (cv != null) cv.visitSource(source, debug);
    }
}
```

如果 `MyClassAdapter` 4.0 扩展 `ClassVisitor` 4.0，一切都会按预期工作。如果我们升级到 ASM 5.0 而不修改自己的代码，`MyClassAdapter` 4.0 现在将扩展 `ClassVisitor` 5.0。但 `api` 字段仍然是 `ASM4 < ASM5`，很容易看出在这种情况下，`ClassVisitor` 5.0 在调用 `visitSource(String, String)` 时的行为与 `ClassVisitor` 4.0 相同。此外，如果新的 `visitSource` 方法以 `null` 的 `author` 被调用，该调用将被重定向到旧版本。最后，如果在输入类中发现非 null 的 `author` 或 `license`，执行将会失败，正如我们的契约所定义的那样（在新 `visitSource` 方法中或在 `visitLicense` 中）。

如果我们升级到 ASM 5.0，并同时更新自己的代码，那么现在得到的是扩展 `ClassVisitor` 5.0 的 `MyClassAdapter` 5.0。`api` 字段现在是 `ASM5`，于是 `visitLicense` 和新的 `visitSource` 方法的行为只是把调用委托给下一个访问者 `cv`。此外，旧的 `visitSource` 方法现在把调用重定向到新的 `visitSource` 方法，这确保如果在变换链中一个旧的类适配器被用在我们自己的适配器之前，`MyClassAdapter` 5.0 不会漏掉这个 visit 事件。

`ClassReader` 总是调用每个 visit 方法的最新版本。因此，如果我们将 `MyClassAdapter` 4.0 与 ASM 4.0 一起使用，或者将 `MyClassAdapter` 5.0 与 ASM 5.0 一起使用，都不会发生间接调用。只有当我们将 `MyClassAdapter` 4.0 与 ASM 5.0 一起使用时，才会在 `ClassVisitor` 中发生一次间接调用（在新 `visitSource` 方法的第 3 行）。因此，尽管旧代码在新 ASM 版本中仍然可以工作，但它运行得会稍慢一些。把它升级为使用新 API 将恢复其性能。

### 5.2.2 继承规则

上述指南对于 `ClassVisitor` 或任何其他类似类的直接子类已经足够。对于间接子类，即如果你定义了一个扩展 `ClassVisitor` 的子类 A1，它又被 A2 扩展，……它又被 An 扩展，那么所有这些子类都必须为同一个 ASM 版本编写。的确，在一条继承链中混用不同版本，可能导致同一个方法的多个版本——例如 `visitSource(String,String)` 和 `visitSource(String,String,String)`——被同时覆写，且行为可能不同，从而导致错误或不可预测的结果。如果这些类来自不同来源、各自独立更新并分别发布，这一性质几乎无法保证。由此引出第二条指南：

**指南 2**：不要使用访问者的继承，而应使用委托（即访问者链）。一个好的做法是默认把你的访问者类声明为 `final` 以保证这一点。

实际上这条指南有两个例外：

- 如果你自己完全控制继承链，并且同时发布该层次结构中的所有类，那么可以使用访问者的继承。此时你必须确保层次结构中的所有类都是为同一个 ASM 版本编写的。仍然要把层次结构中的叶子类声明为 `final`。
- 如果除了叶子类之外没有任何类覆写任何 visit 方法（例如，你只在 `ClassVisitor` 与具体访问者类之间使用中间类来引入便捷方法），那么可以使用「访问者」的继承。仍然要把层次结构中的叶子类声明为 `final`（除非它们也没有覆写任何 visit 方法；在这种情况下，请提供一个以 ASM 版本为参数的构造器，以便子类可以指定它们是为哪个版本编写的）。

[^1]: 实际上我们很可能会添加单个 `visitLicense(String author, String license)` 方法，因为如下文所示，修改方法签名比添加方法更复杂。这里这样做只是为了便于说明。
